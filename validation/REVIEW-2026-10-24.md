## Proposed repairs and observable acceptance checks

These are proposed requirements for flawed fixtures, not changed product rules or
executed workflow tests. Confidence is high for the stated logical gap within each
tiny specification; implementation existence and real-world frequency are unknown.
Priority is local to these fixtures: version is highest because it explicitly
permits unauthorized release; knowledge, ownership, waiting and recovery require
product-specific impact assessment before ranking against each other.

| Pair | Proposed handoff requirement | Given / When / Then check | Unresolved decision |
|---|---|---|---|
| knowledge | A supplies the authorized summary on B's decision surface before action; A retains ownership if unavailable. | Given B lacks private access, when B opens the action, then the permitted summary is available or the action waits without exposing private rationale. | Minimum summary content and fallback timing. |
| ownership | Retain A until acceptance; expose stalled assignment to dispatcher on a defined timer; record acceptance separately from delivery. | Given B has not accepted, when queue delivery succeeds, then an accountable owner still exists. | Timeout, notification surface and escalation service level. |
| version | Show reviewed version and current version; gate release on applicable approval; route new review to authorized approver. | Given only v1 is approved, when publisher attempts v2, then v2 cannot release using v1 evidence. | Any permitted edit exceptions require explicit policy. |
| waiting | Service detects prolonged pending state and gives dispatcher a visible task, authorized alternate and recovery ownership. | Given approver absence, when the specified timer expires, then dispatcher sees the pending item and can reassign without expanding permissions. | Appropriate timer and calendar; fixture control uses elapsed minutes. |
| recovery | Receipt failure creates operator-owned recovery with dispatch identity, completed effect and return/unrecoverable states; requester gets authorized outcome. | Given dispatch already occurred, when cancellation is requested, then dispatch remains recorded and an owner can handle the completed effect. | Return logistics, outcome timing and any irreversible costs. |

## What this reveals

The unchanged skill provides sufficient instructions to explain all five seeded
gaps and why their controls address them in this manual walkthrough. It does not
require a core change on this evidence. Four gaps are missing specifications;
only version freshness is an explicit contradiction. The complete control is
important: adding notifications indiscriminately would manufacture a requirement.

Fixtures are deliberately small and explicit. They do not establish robustness
with long, conflicting sources, implicit skill selection, repeated runs, stale
authorization, duplicate/out-of-order events or the marketplace expiry case.
Those are next-round evaluation candidates. Independent blinded review remains
unexecuted; no detection rate or false-positive rate is claimed.
